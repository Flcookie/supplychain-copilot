# 代码审查与优化建议

> 审查范围：`app/`、`graph/`、`core/`、`rag/`、`tools/`、`tests/` 的核心运行路径。  
> 约束：本次未修改业务代码，只新增本文档。  
> 验证：已运行 `uv run pytest -q`，结果为 `15 passed, 11 subtests passed`。

## 高优先级问题

### 1. 配置在 import 阶段强制依赖外部服务，影响测试和本地开发

位置：
- `core/config.py:38`
- `graph/nodes.py:41`
- `graph/nodes.py:42`
- `rag/retriever.py:19`
- `rag/retriever.py:28`

问题：
- `core/config.py` 在导入时就检查 `OPENAI_API_KEY`、`PINECONE_API_KEY`、`PINECONE_INDEX_NAME`，缺失则直接抛错。
- `graph/nodes.py` 在模块 import 时立即创建 `ChatOpenAI`、多个 retriever。
- `rag/retriever.py` 在模块 import 时立即初始化 Pinecone client、index 和 OpenAI embeddings。

影响：
- 单元测试、静态分析、只测试规则函数时也必须准备 OpenAI/Pinecone 环境。
- Streamlit 启动失败会发生在 import 阶段，错误难定位。
- 无法轻松 mock LLM / retriever，也不利于 CI。

建议：
- 将外部服务初始化改成 lazy factory，例如 `get_llm()`、`get_retriever()`、`get_vectorstore()`。
- 配置校验按运行场景拆分：核心规则测试不需要 Pinecone；RAG 启动才校验 Pinecone。
- 在 graph 构建时注入依赖，便于测试替换。

### 2. KPI 模板中年份参数被忽略，可能返回错误时间范围的数据

位置：
- `tools/kpi_sql_builder.py:336`
- `tools/kpi_sql_builder.py:351`

问题：
- `_defect_rate_by_category(category, year)` 接收 `year`，但 SQL 没有使用年份过滤。
- 如果用户问 “2025 defect rate”，当前 defect rate 查询仍会跨全部年份聚合。

影响：
- 用户以为结果是指定年份，实际是全量数据。
- hybrid / KPI 回答中的 `time_range` 和真实 SQL 结果可能不一致。

建议：
- 和 `_on_time_rate_by_category` 一样，在 `year` 存在时添加日期字段过滤。
- 给这个模板补充测试：同一 category 多年份数据时，指定年份结果必须不同于全量结果。

### 3. “即将过期证书”和“本月 review”使用 `date('now')`，评估结果不可复现

位置：
- `tools/kpi_sql_builder.py:187`
- `graph/nodes.py:745`

问题：
- SQL 直接依赖运行当天的系统日期。
- 评估数据、demo 数据通常是固定快照，但查询窗口是动态的。

影响：
- 同一个问题在不同日期运行会得到不同结果。
- router / RAG / smoke eval 的结果会随时间漂移。

建议：
- 引入配置化 `AS_OF_DATE`，默认取 demo 数据快照日期。
- 所有时间窗口查询用参数传入，例如 `date(?)`，而不是直接 `date('now')`。

### 4. SQL 只读校验是正则级别，存在误判和漏判风险

位置：
- `tools/sql_tools.py:50`
- `tools/sql_tools.py:58`
- `tools/sql_tools.py:63`
- `tools/sql_tools.py:73`

问题：
- `_validate_read_only_sql` 主要通过字符串和正则判断 SQL。
- table allowlist 只识别简单 `FROM table` / `JOIN table`，复杂 CTE、子查询、别名、schema qualifier 容易漏判或误判。
- `blocked = ["insert ", ...]` 会受注释、字符串、大小写/空白变体影响。
- SQLite 连接未显式只读打开。

影响：
- LLM SQL 路径仍然有安全边界不稳的问题。
- 复杂但合法的分析 SQL 可能被拒绝；某些构造 SQL 可能绕过检查。

建议：
- SQLite 使用只读 URI：`sqlite3.connect("file:path?mode=ro", uri=True)`。
- 对 LLM SQL 使用 SQL parser，例如 `sqlglot`，解析 AST 后校验 statement type 和 table references。
- 对执行层增加超时、最大行数、只读连接、禁止 attachment / pragma 等防护。

## 中优先级问题

### 5. Reranker 默认使用 OpenAI embedding，会显著增加每次检索成本和延迟

位置：
- `core/config.py:11`
- `rag/rerank.py:67`
- `rag/hybrid_retriever.py:39`

问题：
- `RERANKER_BACKEND` 默认是 `openai`。
- 每次 `HybridRetriever.invoke()` 都会对 query + candidates 再做 embedding rerank。

影响：
- RAG 每次请求成本更高，延迟更大。
- 本地 demo 或评估批跑时容易被外部 API 限速影响。

建议：
- 默认改为 `none` 或本地 reranker；生产环境显式启用 OpenAI rerank。
- 在评估报告中单独记录 rerank 耗时和调用次数。
- 对相同 query 或相同 candidate pool 做缓存。

### 6. BM25 索引用 pickle 反序列化，存在供应链和本地文件风险

位置：
- `rag/bm25_index.py:10`
- `rag/bm25_index.py:53`

问题：
- `load_bm25_index()` 直接 `pickle.load(f)`。
- pickle 文件位于项目 `data/bm25_index.pkl`，如果被替换，加载时可执行任意代码。

影响：
- 对 demo 项目风险可控，但如果部署或接受外部构建产物，风险较高。

建议：
- 改为 JSON / parquet / sqlite 等安全格式保存 docs 和 tokenized corpus。
- 如果必须 pickle，至少校验文件 hash，并明确只加载本地可信构建产物。

### 7. Router 和 KPI parse 的 JSON 解析失败被静默吞掉

位置：
- `graph/nodes.py:239`
- `graph/nodes.py:366`
- `graph/nodes.py:635`

问题：
- LLM 输出 JSON 解析失败后直接 `pass`，只使用默认值。
- `state` 中没有记录 parse error、raw output 或 fallback 原因。

影响：
- 线上问题难排查：用户看到路由错了，但日志里没有原始失败信息。
- eval 无法区分“模型判断错”和“JSON 格式坏了”。

建议：
- 在 `route_decision` / `kpi_parse` 中保留 `parse_error` 和截断后的 `raw_output`。
- 对 router JSON 使用更严格的 schema 校验。
- eval 中单独统计 parse failure rate。

### 8. 风险场景存在默认供应商 ID，可能误导用户

位置：
- `graph/nodes.py:750`
- `graph/nodes.py:772`

问题：
- 质量问题场景缺少 supplier id 时默认 `SUP021`。
- blacklist 场景缺少 supplier id 时默认 `SUP030`。

影响：
- 用户未指定供应商时，系统会拿一个固定供应商回答，看起来像真实匹配结果。
- 高风险场景尤其容易造成错误业务判断。

建议：
- 缺少供应商 ID 时返回 clarification，而不是默认供应商。
- 对 blacklist / status change 等 HITL 场景强制要求实体确认。

### 9. Evidence 中的 simulation 公式和数据快照仍是旧 schema

位置：
- `core/evidence.py:177`
- `core/evidence.py:179`
- `graph/nodes.py:52`

问题：
- `simulation_evidence()` 写的是 `COUNT(p.id), SUM(p.qty)` 和 `supplychain_kpi.db`。
- 当前 graph 风险场景实际使用的是 Ratti demo schema，例如 `po_id`、`order_amount_eur`、`ratti_copilot_demo.db`。

影响：
- UI 展示的计算说明和真实 SQL 不一致。
- 证据链会降低可信度。

建议：
- Evidence 不要硬编码旧公式和旧 DB 名称。
- 由 scenario node 按实际 SQL 类型传入 metric definition、formula、data snapshot。

### 10. Streamlit 中存在未使用的全局 graph 构建

位置：
- `app/ui.py:35`
- `app/ui.py:340`

问题：
- 文件加载时先执行 `graph = get_graph(_graph_cache_key())`。
- 实际请求时 `run_copilot()` 又重新通过 `get_graph(_graph_cache_key())` 获取 active graph。

影响：
- 首次启动可能重复触发昂贵初始化。
- 代码含义不清：全局 `graph` 实际没有被使用。

建议：
- 移除未使用的全局 `graph`，统一在 `run_copilot()` 或初始化阶段获取。

## 低优先级 / 可维护性问题

### 11. UI 和规则文件里有大量硬编码文案，国际化维护成本高

位置：
- `app/ui.py:37`
- `app/ui.py:54`
- `core/qualification_rules.py`

问题：
- demo 场景、sidebar、中文映射、业务规则都写在 Python 文件里。
- 文案和业务规则混在一起，改文案也容易影响逻辑代码 review。

建议：
- 将 UI i18n 文案拆到 `locales/en.json`、`locales/zh.json`。
- 将 qualification category/rule 配置拆成 YAML/JSON，代码只负责读取和执行规则。

### 12. `sys.path.append` 属于脚本式补丁，不利于包化运行

位置：
- `app/ui.py:2`

问题：
- 通过修改 `sys.path` 解决导入路径，说明项目包结构和运行入口还不够规范。

建议：
- 用 `python -m app.ui` 或在 `pyproject.toml` 中配置 package / script entry。
- 保持所有模块通过项目根包路径导入。

### 13. Streamlit 人为 sleep 没有实际价值

位置：
- `app/ui.py:378`

问题：
- `time.sleep(0.2)` 只增加响应延迟，不解决状态同步问题。

建议：
- 删除 sleep；如果要展示 loading，用 `st.spinner` 或状态占位即可。

### 14. README / 控制台输出可能存在编码显示问题

位置：
- `README.md`
- `app/main.py:12`
- `core/config.py:41`

问题：
- PowerShell `Get-Content` 输出中 README 和部分中文/emoji 文案出现 mojibake。
- 测试文件中的中文通过 `rg` 显示正常，说明可能是文件编码、终端编码或部分文件实际混杂编码导致。

影响：
- GitHub / Windows PowerShell / Streamlit 上展示可能不一致。
- 面试或作品集展示时会影响第一印象。

建议：
- 统一所有文本文件为 UTF-8。
- 避免在核心配置 import 时直接 `print` 调试信息；改用 logging，并允许关闭。

## 测试覆盖建议

当前测试主要覆盖 qualification checklist，测试结果通过。但核心风险路径缺少自动测试：

- `tools/sql_tools.py`：只读 SQL、非法 SQL、allowlist、limit、只读连接。
- `tools/kpi_sql_builder.py`：每个模板的 SQL、参数、年份过滤、空结果。
- `graph/graph.py`：低 confidence、ambiguity、baseline mode、各 intent 路由。
- `graph/nodes.py`：router JSON 解析失败、KPI parse 失败、unsupported metric、scenario 缺少 supplier id。
- `rag/hybrid_retriever.py`：BM25 + vector 融合排序、doc_type filter、rerank 关闭/开启行为。
- `core/evidence.py`：Evidence Contract 和实际 SQL schema 一致性。

建议先补一层不依赖 OpenAI/Pinecone 的纯单元测试，再把 RAG/LLM 路径放到单独 integration test 或 eval pipeline。

## 建议处理顺序

1. 先修 KPI 年份过滤、scenario 默认供应商、simulation evidence 旧 schema 这三类会直接影响答案正确性的 bug。
2. 再重构配置和外部服务初始化，降低测试和部署成本。
3. 然后加强 SQL 安全边界，把只读连接和 SQL AST 校验补上。
4. 最后整理 UI/i18n 文案、README 编码和未使用代码。
